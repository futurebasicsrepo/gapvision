# QA sweep — 18 August 2026

A full pass over every module against a real Postgres, with the four frontends
built and previewed and both services running. Everything below was reproduced
on a live stack, not read off the source.

**What passed:** 483 Python tests, and 17 of the 19 browser/integration suites
once they were given credentials that match the seeder. The four pillars —
ask, requests, presence, comms — all work end to end. The privacy architecture
holds up under test: consent classes are enforced, presence expires, credentials
are sealed, and the anonymous request path genuinely needs no customer record.

**What follows is what did not.** Ordered by what it costs us, not by where it
sits in the tree.

## P0 — A wrong answer, in the demo we sell on

`packages/ai-service/app/voice.py:289` — `size_availability()`

Asking *"do you have the barrel jean in a 32"* against the seeded demo store
answers **"No 32 in the High Rise Barrel Jeans on the floor."** There are three,
in `32x30`.

```
sizes: {"26x28": 1, "28x30": 3, "30x30": 2, "32x30": 3, "34x32": 0}
"32"    -> No 32 ... on the floor      (wrong — 3 in stock)
"28"    -> No 28 ... on the floor      (wrong — 3 in stock)
"32x30" -> Yes. 3 ... at Denim Wall    (right)
```

Two defects in one function:

1. **Exact string match only.** `"32"` never equals `"32x30"`, so a waist-only
   question can never match a `WxL` catalogue. Nobody on a shop floor asks for
   a 32x30 — they ask for a 32. The codebase already knows these schemes are
   compatible: `_scheme_compatible()` explicitly treats `{numeric, waist}` as a
   match, which is why product resolution correctly binds "32" to the jean. The
   availability check then contradicts it.
2. **The fall-through returns a confident `("no", 0)`.** When the size key isn't
   in a scheme we recognise, the honest answer is `unknown`, and the function's
   own docstring says so. Today that honesty only applies when `sizes` is missing
   entirely.

Why this is P0 rather than a bug: it is the exact failure the customer deck
promises we do not make — *"An associate who gets confidently told the wrong
thing twice stops using the tool, and they are right to."* It is also the
literal question the deck uses three times, on the seeded store the deck offers
to demo against. Our sales process is "ask it something you already know the
answer to." Right now that demo can fail on the first question.

`test_size_availability_is_honest_without_variant_data` covers the missing-`sizes`
case only. There is no test for a size key outside the catalogue's scheme.

## P0 — Two endpoints on the realtime proxy accept unauthenticated callers

`packages/server/src/proxy.js` — the roster route and the guest-context route.

Both are reachable with no token. The guest-context response carries the full
clienteling package: name, address, contact, purchase history, sizes, loyalty
tier and points. The roster route is meant to be gated behind a flag, but the
tenant check has a hardcoded exemption that leaves the demo tenant open
regardless of the flag.

The source already knows: *"this is still open to anyone who can reach the
realtime server — the proxy protects the AI service, it does not authorize the
caller."* Its stated mitigation is to keep the realtime server's URL off public
pages. That mitigation does not hold — the URL is compiled into the shipped
plugin bundle, and `test:bundle` asserts that it is.

**The data exposed today is seeded and synthetic.** The chain is the problem,
and it needs closing before any real store is connected to a tenant the roster
exemption covers.

This also contradicts a claim we make in the section of the deck written for a
general counsel: *"There is deliberately no endpoint that enumerates your
customers."* Today there is one.

Fix is the one the comment already proposes: require a session id issued by
check-in, so a guest card can only be fetched for a guest who just consented.

## P1 — Console's decode has no screen-reader text

`packages/internal/src/components/Decode.jsx`

Studio's copy builds a visually-hidden span carrying the real string and marks
the animating characters `aria-hidden`. Console's does not. Console puts the
page `<h1>` through it with `replay={view}`, so the title re-scrambles on **every
panel change** — a screen-reader user navigating Console hears a fresh run of
random glyphs each time, which is precisely the problem Studio's version exists
to solve.

Related: Studio's `Decode.jsx` carries a comment saying the file *"exists twice
and the behaviour must stay identical. Change both or neither."* That is not
true and has not been for a while — the two use different class names
(`dc-c` vs `decode-char`), expose different props, and only one is accessible.
The comment should either become true or stop claiming to be.

## Pitch vs. product

Checked every falsifiable claim in the customer deck against the code.

### Claims that do not hold

**"It routes to whoever is nearest."** It routes by *assigned zone*
(`pushRequest`, `server/src/index.js`): an associate whose zone matches gets it,
and an associate with no zone set gets everything. There is no proximity concept
anywhere in the codebase. In a store that hasn't tagged zones this is a
broadcast, not routing. The code comment has the honest sentence already —
*"whoever covers that zone."*

**"Phone — Requests, answers, comms and the customer card. This is where a pilot
starts."** Pocket's entire action set is `claim | release | end | floor:message |
mark`. The voice socket events are emitted only from the glasses plugin. **An
associate cannot ask a question from the phone.** They can receive an answer
pushed to them; they cannot initiate one. (Note also that Studio's
`AssociateView` labels a *typed* radio input "Push to talk…", which reads as
voice and isn't.)

**"There is deliberately no endpoint that enumerates your customers."** See the
P0 above.

**"Self-serve · Shopify — $79–149 per location / month. Monthly, no minimum
term."** There is no signup, no payment integration, no metering, and no
per-location counting. `billing_plan` is a dropdown a CueSea admin sets by hand
when they create the tenant. Every tenant that will ever exist has to be
provisioned by us. This is the tier the pricing page leads with.

### A claim that undersells us

**"Empty is not the same as absent — the current engineering priority, ships
before any pilot starts."** This is built, and enforced in `vision.py`,
`checkout.py`, `crm_shopify.py`, `barcode.py` and `voice.py`. It should move out
of Known Edges. The one place it is currently broken is the P0 above — which is
also the place it matters most.

### Claims that hold

Camera-free, with no camera path in the codebase. 45-minute presence expiry.
AES-256-GCM per-tenant credentials under a key the database never holds. Consent
classes enforced at the door — a caller claiming a stronger door than it holds is
refused, verified live. The anonymous request path works with a client-generated
reference and no customer record, exactly as claimed. Shopify variant-level
stock, abandoned checkouts, and tier derived from lifetime spend. Answer latency
is instrumented per query and surfaced. Retention sweeps leave receipts.

## The GTM opportunity, argued honestly

### What is genuinely strong

The wedge is narrow and legible: *the answer, where the customer is.* Camera-free
is a real legal accelerator, not a marketing line — it is the difference between
clearing a GC in a two-party-consent state and not clearing at all, and it is a
durable differentiator against anyone doing vision-based clienteling.

The demo *is* the sales process, and that is the cheapest high-conversion motion
available to a company this size. The Known Edges slide is a genuine trust asset
with technical buyers. The pilot design — holdout, kill criteria agreed before
week one — is credible to an ops buyer who has been sold to before.

### The central contradiction

**The pricing tiers and the integration reality point at two different
companies.**

The self-serve tier matches Shopify's install base — and does not exist. The
chains tier ($50–150k, 10–50 stores) exists as a motion, but chains at that size
overwhelmingly do not run Shopify POS; they run Aptos, Xstore, NCR, Manhattan. So
the tier we can sell has no adapter, and the tier we have an adapter for has no
product to sell.

The deck half-admits this ("a second POS adapter, driven by whoever signs
first"), but the sequencing means the first chain deal is an integration project
of unknown length *before* the pilot that was supposed to de-risk it. That is a
hard thing to close.

Pick one and make the deck match:
- **Self-serve is the business.** Then signup, Stripe, and Shopify App Store
  distribution are the roadmap, and the chains slide comes out.
- **Pilots are the business.** Then the self-serve tier comes off the pricing
  page, and the first non-Shopify adapter gets scoped now rather than after a
  signature.

My read: pilots. Self-serve at $79 needs docs, support and an install base we
don't have, and the evidence that makes everything else sellable comes from a
measured pilot. But that means the pricing page is currently aimed at the wrong
reader.

### The pilot may be underpowered for the number it promises

*"The one number we are trying to move: incremental revenue per associate per
shift."* That is the honest metric and the right instinct. It is also a high bar:
twelve weeks, one store, against normal retail variance. There is a real chance
of running a rigorous pilot and reporting no detectable difference on a product
that genuinely worked.

The effects we can measure cleanly and already instrument are time-to-answer and
request resolution rate. I would make one of those the **primary** endpoint,
with revenue as a declared secondary. That keeps the intellectual honesty that
makes the kill-criteria slide valuable, without betting the deal on a
statistically fragile endpoint.

### Ask-on-phone is a strategy decision, not a backlog item

The deck's competitive claim is that this is *"an interaction difference, not a
feature difference"* — the answer arrives instead of being searched for. That
difference **is** Ask. With Ask on glasses only, a phone pilot is requests plus
comms plus a customer card, which is a good product that looks much more like
existing clienteling and task tools.

So: either Ask ships on the phone, or the pilot runs on glasses (six-hour
batteries, eight-hour shifts, by our own admission), or the competitive claim
weakens. This is the most consequential item in this document after the P0s.

### Smaller GTM notes

- **Zones are load-bearing for two claims** — routing and answer specificity
  ("on the denim wall" vs "on the floor") — and are currently a known edge. Zone
  tagging should be a gated deliverable in weeks 0–2, not a footnote.
- **No named reference.** "Retail is live today" with no logo, alongside
  hospitality and field service "looking for design partners", is a hard read for
  a chain. One named pilot changes the deck more than any feature here.
- **The entry persona isn't named.** The deck speaks to a GC in §06, an ops lead
  in §08 and a founder in §09. For a $50–150k specialty-retail deal the door is
  usually VP Retail Ops or Director of Store Experience. The demo CTA should be
  written to that person.

## And the thing underneath all of it

There is still no `.github/workflows`. The five green checks on every recent PR
are Vercel builds — nothing has ever run a test on a pull request. The Studio
dashboard regression above is exactly the class of bug CI exists to catch, and it
sat there unnoticed.

Every merge so far has shipped on a local test run and my word for it. That is
the cheapest thing on this list to fix and the one that changes the most.
